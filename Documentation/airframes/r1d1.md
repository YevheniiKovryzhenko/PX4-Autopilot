# R1D1 — CAN avionics and spray-actuator quadrotor

## Build and select

From the selected PX4 checkout:

```sh
make cubepilot_cubeorangeplus_surgeon -j4
```

Upload `build/cubepilot_cubeorangeplus_surgeon/cubepilot_cubeorangeplus_surgeon.px4` using QGroundControl’s **Custom Firmware** option. Fully close and restart QGC to see the new airframes, then select **R1D1** (ID **22010**) and apply/reboot the flight controller. This build defaults to `SIMULINK_MODE=0` and retains stock quadrotor control. It does not select the airframe automatically or erase saved settings.

For model integration, build `cubepilot_cubeorangeplus_simulink` (stock control plus additional tasks) or `cubepilot_cubeorangeplus_simulinkctrl` (external control). See [common setup](../../src/modules/simulink_io/README.md) for startup modes, shared disarming defaults, parameter precedence and telemetry controls. Firmware preset source: [22010_r1d1](../../ROMFS/px4fmu_common/custom_airframes/init.d/airframes/22010_r1d1).

## Sensors and preset parameters

The airframe uses avionics node 70, including the alternative combined 70/71 image, on 1 Mbit/s DroneCAN. Sensors are the horizontal SF45/B scan, downward US-D1 radar altimeter, forwarded Here4 GPS/compass and optional DroneCAN airspeed. The Pixhawk node ID is 1. Peripheral power is supplied separately.

| Parameter/default | Purpose |
| --- | --- |
| `UAVCAN_ENABLE=3`, `UAVCAN_BITRATE=1000000`, `UAVCAN_NODE_ID=1` | Sensors, actuators and node services on the Pixhawk; ID distinct from peripheral nodes |
| `UAVCAN_SUB_GPS=1`, `UAVCAN_SUB_MAG=1`, `UAVCAN_SUB_RNG=1`, `UAVCAN_SUB_DPRES=1` | Receive supported avionics sensor types |
| `GPS_1_CONFIG=0`, `GPS_2_CONFIG=0` | Avoid starting unused serial GPS ports |
| `SENS_EN_SF45_CFG=0`, `SF45C_ENABLE=1` | Use the CAN SF45 path instead of a local serial SF45 driver |
| `SF45C_NODE=70`, `SF45C_SENSOR=0`, `SF45C_ORIENT=24`, `SF45C_YAW=0`, `SF45C_TIMEOUT=100` | SF45 source, upright horizontal scan and forward mounting reference; verify mounting |
| `CP_DIST=1.0`, `MPC_POS_MODE=4`, `CP_GO_NO_DATA=0` | Enable Position-mode collision prevention from the SF45 scan with 1 m clearance; block motion into unobserved directions |
| `EKF2_RNG_CTRL=1`, `MPC_ALT_MODE=1` | Conditional downward-range height aiding and terrain following; retain the existing primary height reference |

| `UAVCAN_SV_FUNC6=105`, `UAVCAN_SV_FUNC7=106`, `UAVCAN_SV_FUNC8=107` | Motor functions 5–7 on CAN slots 6–8, matching AP_Periph actuator IDs 5–7 and PWM pads 1–3 |
| `UAVCAN_SV_MIN6..8=0`, `UAVCAN_SV_MAX6..8=1000`, `UAVCAN_SV_REV=0` | Full unitless CAN range maps to the node's 1000–2000 µs ESC range, with no reversal |

## TELEM1 telemetry and RFD reference

The following PX4 defaults are part of the R1D1 preset. Select the airframe and reboot to load them; existing saved overrides remain in effect. The radio itself is configured separately and is not reprogrammed by PX4 firmware upload.

| PX4 parameter | Default | Purpose |
| --- | ---: | --- |
| `MAV_0_CONFIG` | 101 | Assign link 0 to TELEM1 |
| `SER_TEL1_BAUD` | 230400 | UART baud matching the configured radio |
| `MAV_0_FLOW_CTRL` | 1 | Force RTS/CTS hardware flow control; handshake wires are required |
| `MAV_0_RATE` | 18000 | Maximum MAVLink output budget, B/s; not guaranteed RF throughput |
| `MAV_0_MODE` | 15 | Normal message set plus parameter-controlled Simulink telemetry overrides |
| `MAV_0_RADIO_CTL` | 1 | Allow throttling from the radio's `RADIO_STATUS` reports |
| `MAV_0_FORWARD` | 0 | Disable forwarding between MAVLink links; does not disable DroneCAN reception or node CAN1/CAN2 mirroring |

The flow-control parameter is `MAV_0_FLOW_CTRL`, not `SER_TEL1_FLOW`. Onboard profile 2 does not apply the custom standard-stream rate parameters. USB remains a separate link. An 18 kB/s budget is a ceiling: RF framing, TDM, return traffic and link quality affect achieved throughput.

### Radio-side configuration record

This table records the reported RFD900x/ux setup for future reference, not settings applied by the flight-controller preset. Register numbers below follow the [RFDesign peer-to-peer V3.x manual](https://rfdesign.com.au/wp-content/uploads/2024/04/RFD900x-Peer-to-peer-V3.X-User-Manual-V1.4.pdf); confirm actual parameter names, values and allowed ranges with RFD Tools or `ATI5` / `ATI5?` on each radio. The exact installed model/firmware remains unverified.

| RFD parameter | V3.x register | Recorded value | Notes |
| --- | --- | ---: | --- |
| `SERIAL_SPEED` | S1 | 230 | UART 230400 baud; match PX4 on the aircraft and the host serial connection on the ground |
| `AIR_SPEED` | S2 | 224 | RF rate, kbit/s; match both radios and use a supported regional value |
| `NETID` | S3 | 60 | Match both radios |
| `TXPOWER` | S4 | 30 | Requested transmit power, dBm; subject to the installed regional modem's limits |
| `ECC` | S5 | 0 | Error-correction coding disabled |
| `MAVLINK` | S6 | 1 | MAVLink framing and radio-status reporting |
| `OP_RESEND` | S7 | 0 | Opportunistic resend disabled |
| `MIN_FREQ` | S8 | 902000 | Reported lower bound, kHz; verify against the actual US-region configuration |
| `MAX_FREQ` | S9 | 928000 | Reported upper bound, kHz; verify against the actual US-region configuration |
| `NUM_CHANNELS` | S10 | 50 | Reported hopping-channel count; not a generic compliance prescription |
| `DUTY_CYCLE` | S11 | 100 | Configured duty-cycle limit, percent |
| `LBT_RSSI` | S12 | 0 | Listen-before-talk threshold setting |
| `RTSCTS` | S13 | 1 | Hardware serial flow control enabled |
| Max Window (`MAX_WINDOW` label may vary) | S14 | 33 | TDM window, ms; smaller windows can trade throughput for latency |

In this manual, S15 is the encryption-level register, not Max Window. Preserve the radio's valid region/certification settings rather than applying a generic frequency/hop-count table blindly. Both radios must agree on their required RF/link settings; reducing Max Window does not guarantee a fourfold reduction in total round-trip latency.

## Actuators and connections

The output mapping targets the combined `Aircraft-G474-70-71` image using numeric node ID 70, or the standalone actuator image on node 71. The avionics-only `Aircraft-G474-70` image has no assigned actuator outputs. Motor functions 5, 6 and 7 identify the pump, nozzle 1 and nozzle 2 respectively, separate from flight motors 1–4. The `UAVCAN_SV` prefix selects the existing ArrayCommand transport; the assigned Motor functions supply motor prearm/arming gating. The node and both stock drivers are unchanged. Stock quadrotor allocation only drives flight motors 1–4; auxiliary motors require actuator-test commands or a control source that supplies `actuator_motors.control[4..6]` without competing with the flight allocator. Pads 5/6 remain valve GPIOs on hardpoint IDs 0/1; they are not servo slots, and automated two-valve command integration remains outstanding.

| Pixhawk connection | Connected device / role | Mapping |
| --- | --- | --- |
| CAN1 H / L / GND | Node CAN1 H / L / GND | Avionics node 70, including the combined image |
| Node CAN2 H / L / GND | Here4 CAN H / L / GND | Bidirectional forwarding; separate segment termination |
| MAIN 1–4 | Flight ESC signal inputs | Motor 1–4; local PX4IO outputs |
| Node pads 1 / 2 / 3 | Pump / nozzle 1 / nozzle 2 ESC signals | Motor 5 / 6 / 7 through CAN slots 6 / 7 / 8 |
| Node pads 5 / 6 | Valve 1 / 2 BEC enable inputs | Hardpoint IDs 0 / 1; command integration pending |
| TELEM1 TX / RX / GND | RFD RX / TX / GND | MAVLink link 0, 230400 baud; match the modem UART setting |
| TELEM1 RTS / CTS | RFD CTS / RTS | Required handshake connections for forced hardware flow control |
| RC IN / SBUS | SBUS receiver | Existing RC input path; separate PWM capture driver not required |

The MAIN assignments and enabled PWM drivers do not require a stock-driver modification. For node pin labels, sensor serial wiring and termination, use the paired AP_Periph checkout's `Tools/AP_Periph/aircraft/node-70.md`, `node-70-71.md` and `can-wiring.md`. Avoid duplicate numeric node IDs or duplicate actuator responders.

The SF45 is upright above the aircraft, scanning an X–Y plane, with its forward reference aligned to the nose. The CAN rangefinder bridge reports the US-D1 as downward facing along body +Z. Enter the actual downward-sensor position using `EKF2_RNG_POS_X/Y/Z` in metres relative to the body origin/centre of gravity (+forward, +right, +down); the preset leaves these unmeasured offsets at zero. Those EKF offsets do not describe the SF45 scanner. Node safety may suppress PWM pulses when disarmed even though the configured low command corresponds to 1000 µs; bench-check ESC initialization and CAN-loss behavior.

## Commissioning

For a first test, disconnect propellers and pump/nozzle loads, connect a powered dummy servo, confirm the peripheral is visible in the CAN node list, and use QGroundControl's actuator test for the matching Motor 5, 6 or 7 function. Check `uavcan status`, `lightware_sf45_can status`, `listener sensor_gps`, `listener distance_sensor` and `listener sf45_sample`. Verify the range sources separately and confirm CAN2-forwarded devices are visible and configurable. A software build cannot establish correct wiring, orientation or servo travel.

In `surgeon` with `SIMULINK_MODE=0`, the stock quadrotor estimator, flight-mode manager, controllers and allocator remain active. `simulink` mode 1 also retains them; `simulinkctrl` mode 2 deliberately omits stock control. Collision prevention limits pilot commands in Position mode; it does not provide autonomous mission obstacle avoidance or lidar-based localization. `CP_DIST=1.0` is measured from the sensor, so check clearance against the airframe and rotor envelope. With `CP_GO_NO_DATA=0`, blind sectors or stale scan data restrict motion. Conditional range aiding uses the stock low-speed/low-height limits (1 m/s and 5 m unless changed); terrain following maintains commanded height above the estimated ground during horizontal motion and reverts to earth-frame altitude control if the ground-distance estimate becomes invalid. Check sensor mounting, range validity, actual sensor offsets and collision-prevention behavior before flight. Saved values can override these preset defaults.

US-D1 limits follow the [manufacturer specification](https://ainstein.ai/us-d1-all-weather-radar-altimeter/): 0.5–50 m, with a blind zone below 0.5 m. Node 70 and combined 70/71 also preset `RNGFND1_MIN=0.5` and `RNGFND1_MAX=50.0`; otherwise the upstream node defaults mark readings above 7 m out of range. Saved node parameters must be updated separately from Pixhawk parameters. The bounds do not turn the radar into a valid ground-height source below its blind zone.

No validated US-D1-specific PX4 noise setting was found. Published 4–6 cm precision is not a stated Gaussian standard deviation. The preset therefore explicitly retains PX4's conservative baseline, rather than deriving covariance from that specification. In the checked EKF implementation, range measurement variance is `R(h) = 0.10² + (0.05 × h)²` in m², with `h` the tilt-corrected ground distance in metres; the fixed variance term is 0.01 m². [PX4 recommends tuning range noise and obstruction detection against flight data](https://docs.px4.io/v1.17/en/advanced_config/tuning_the_ecl_ekf#range-finder-obstruction-detection). Keep the stock innovation gates and delay until measurements justify changes.

The [US-D1 manual](https://ainstein.ai/wp-content/uploads/US-D1-Technical-User-Manual-D00.02.05.docx.pdf) requires rejection of low-SNR readings (13 dB or lower). The existing node UART driver checks packet integrity but does not apply this SNR rejection, and the CAN bridge's validity flag is not an SNR-based confidence measurement. This remains an integration limitation; changing EKF noise does not implement the missing quality filter. No stock driver code is changed by these presets.

## Simulation

```sh
make px4_sitl_simulink gz_r1d1
make px4_sitl_simulinkctrl gz_r1d1
```

The simulator uses the existing S500 dynamics and output mapping. The wrapper does not apply hardware CAN presets and does not reproduce the real vehicle's mass, propulsion or physical sensor wiring.
